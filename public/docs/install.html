INSTALL POSTSTEWARD

One command, then connect your destinations.

The installable client brings PostSteward to a human terminal or an agent runtime. Provider OAuth, owner authority and durable provider-effect receipts remain in the hosted PostSteward control plane.

macOS, Linux and WSL2

curl -fsSL --proto '=https' --tlsv1.2 https://poststeward.com/install.sh | bash

The installer is no-root and user-local. It requires Python 3.10+ and installs poststeward under ~/.local/bin by default.

poststeward --version
poststeward onboard

Connect X, Threads and LinkedIn.

poststeward onboard opens the owner workspace. Sign in, connect any combination of X, Threads and LinkedIn, verify the stable destination identity, then create a scoped and expiring agent grant.

Provider consent stays human-owned.

The CLI never turns a successful install into publishing authority. Provider applications, connected identities and agent grants remain separate states.

Agent surface

poststeward help --json
poststeward status
poststeward providers
poststeward receipts
poststeward invoke workspace_status '{}'
poststeward mcp

The generic invoke command calls the same operation catalogue used by HTTP and remote MCP. Consequential calls retain PostSteward's idempotency, owner-review and receipt boundaries.

Automation / CI

curl -fsSL https://poststeward.com/install.sh | bash -s -- --no-onboard
curl -fsSL https://poststeward.com/install.sh | bash -s -- --dry-run
curl -fsSL https://poststeward.com/install.sh | bash -s -- --version <40-char-sha>

Use POSTSTEWARD_TOKEN for deliberate non-interactive agent runs rather than writing a token into command history.

Why provider credentials are not copied locally

PostSteward already owns the hosted provider-effect ledger and durable receipts. A second independent provider writer on the same account would create split-brain authority. The local client therefore stores only the scoped agent grant; provider credentials remain server-side.
